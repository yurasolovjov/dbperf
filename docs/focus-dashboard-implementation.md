# Дашборд «Фокус»

Источник визуальных требований — утверждённый вариант `03-focus.html`, версия 9.
Реализация находится в `services/dbperf-ui`, обработка фильтров — в
`services/dbperf/internal/query`. Использованы навыки frontend-engineering,
backend-engineering и database-engineering из пользовательского каталога skills.

## Интервалы и состояние

- Общий период: 1, 5, 15 минут, час, 24 часа или произвольный интервал до 30 дней.
- Произвольные даты и все подписи используют UTC+3 независимо от часового пояса ОС.
- Верхний график показывает общий период; его окно задаёт область нижнего графика.
- Окно нижнего графика задаёт интервал показателей и таблицы.
- Окна хранят относительные координаты: вложенное выделение сохраняет положение
  при перемещении и изменении ширины родительского окна. Изменение периода сбрасывает окна.
- Края и центр окна доступны мышью, касанием и клавиатурой. Стрелки двигают окно/край,
  Shift увеличивает шаг, Home/End перемещают к границе. Есть кнопки сдвига и масштаба.
- Повторный клик по выбранной легенде снимает её фильтр. Общий SQL-фильтр независим.
- Фильтры таблицы сохраняются между вкладками и AAS/%; их изменение сбрасывает страницу.
- Периодические обновления можно выключить. Ручное обновление повторяет запросы
  даже для фиксированного периода и закреплённых окон.
- Данные при изменении контекста очищаются; ответы отменённых запросов игнорируются.

Графики рисуются SVG по реальным временным меткам и значениям API. Пропуски снимков
не соединяются линией; значения удерживаются в пределах бакета. Пик относится к
бакетам фактического шага API, а не к невидимой мгновенной нагрузке. Цвета ожиданий
переиспользованы из существующего приложения. Основной график — линия общей активности
и отдельные линии разреза. Весь дашборд входит в Fullscreen API; предусмотрен CSS fallback.

## SQL-фильтрация

Контракт расширен обратно совместимыми полями protobuf:

- `Filter.match`: `MATCH_VALUES` (прежнее IN/NOT IN), `MATCH_CONTAINS`,
  `MATCH_TEXT_EQUALS`; `exclude` инвертирует условие.
- `ActivityTopRequest.table_filters`, `aas`, `percent`, `page_size`, `offset`.
- `ActivityTopResponse.matched_rows`, `level`.

Текстовые условия выполняются в WHERE до группировки. Содержит — буквальный
регистронезависимый поиск `positionCaseInsensitiveUTF8`, без wildcard-семантики `%`/`_`.
Поиск QUERY выполняется по полному сохранённому SQL в `pg_query_texts`, а не по
64-символьной подписи. Версии текста сворачиваются через `argMax(query, last_seen)`
по хешу с обязательным ограничением `target_id`, затем используются как множество
для фильтрации активности. Дубликаты текста не умножают число сессий.

Числовые пределы выполняются в HAVING после GROUP BY и до LIMIT/OFFSET.
Процент считается от активности после категориальных фильтров, но до числовых:
исключение строк по AAS/% не перенормирует долю оставшихся строк.
AAS использует число снимков объекта, включая снимки с нулём активных сессий.
Нулевые знаменатели обрабатываются явно. Фильтры комбинируются AND,
несколько значений внутри одного условия — OR. Пустые границы диапазона не ограничивают его;
нулевая граница сохраняет присутствие в protobuf.

Пагинация: до 100 строк на запрос, в интерфейсе 8. Порядок `n DESC, slice`
детерминированный; синтетического other в постраничной выдаче нет. Между отдельными
запросами при продолжающемся сборе ранг может меняться: это не snapshot-пагинация.
Без `page_size` сохраняется прежний top-N с остатком для старых потребителей.
Все значения передаются параметрами драйвера, SQL-выражения измерений выбираются из enum.
Запросы PID и фильтры PID явно используют raw-уровень даже при крупном шаге;
за пределами настроенного raw_range_limit API возвращает ошибку вместо неверных данных.

Новых таблиц, индексов и миграций нет. На локальном ClickHouse 25.8 проверен
EXPLAIN с фильтром SQL: ограничение target/time использует существующий первичный ключ
pg_activity, подзапрос текстов ограничен target_id. Проверка на небольшом pgbench-стенде
не является нагрузочным измерением для production.

## Профиль и таблица

Профиль сохраняет порядок измерений и пути API. По умолчанию первый уровень — SQL:
обычный клик открывает текст, отдельная кнопка раскрывает следующий уровень.
Карточки имеют минимальную ширину 180px (в пределах доступной ширины) и переносятся.
Показаны настоящие доли, даже когда ширина карточки ограничена минимумом.
На уровне показывается 100 узлов, остальные доступны через «Показать ещё».
Запрашивается до 20000 путей, непокрытая активность отмечается явно.

SQL диалог использует native dialog для фокуса, Escape и top layer в fullscreen.
Копирование имеет Clipboard API и fallback; добавление в общие фильтры использует
строковый uint64-хеш, без преобразования в JavaScript number.

## Проверки и запуск

```sh
# frontend
cd services/dbperf-ui
npm ci
npm run typecheck
npm test
npx playwright install chromium
npm run test:e2e
DBPERF_LIVE=1 npm run test:e2e  # требует запущенный compose
DBPERF_UI_URL=http://127.0.0.1:8081 DBPERF_LIVE=1 npx playwright test -g "live stack"
npm run test:coverage

# backend
cd services/dbperf
go test -race ./...
go vet ./...
buf lint
DBPERF_TEST_CLICKHOUSE=127.0.0.1:19000 go test ./internal/query -count=1
```

Интеграционный Go-тест создаёт и удаляет только собственную тестовую БД в явно
указанном ClickHouse. Без DBPERF_TEST_CLICKHOUSE он пропускается.
Playwright использует HTTP fixtures для воспроизводимых размеров и 80 SQL-карточек;
отдельный live-тест проверяет настоящий SQL-поиск, смену вкладки и полный текст на pgbench.
Проверены 1024×768, 1280×800, 1366×768, 1440×900, 1920×1080, 768×1024,
390×844 и 320×740. На телефоне таблица имеет собственную горизонтальную прокрутку;
страница не выходит по ширине. Раскрытые строки, чипы и длинный профиль увеличивают высоту.

Порог владельца 90% строк/ветвей задан в Vitest для всего src, включая
неимпортированные файлы. Текущий набор тестов этот порог НЕ проходит; успешные unit/E2E
проверки не означают прохождение coverage gate. Стандартный Go coverage измеряет
statements, а не branches/lines. Отчёт о покрытии и доведение до порога — отдельный
незавершённый критерий качества, не скрытый исключениями. Исходный проект не имел
CI; автоматического CI gate для обоих сервисов пока нет.

Развёртывать сначала backend, затем frontend: новый интерфейс ожидает matched_rows
и серверную фильтрацию. Откат UI совместим с расширенным backend. Схема БД не меняется.
Локальный стенд запускается штатным `make up`; данные pgbench являются тестовыми.
